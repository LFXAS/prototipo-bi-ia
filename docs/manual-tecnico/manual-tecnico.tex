\section{Propósito y audiencia}

Este manual permite instalar, levantar, comprobar, mantener y replicar el ambiente técnico del prototipo. Está dirigido a las autoras, docentes revisores, colaboradores autorizados y personal técnico que necesite reproducir la demostración.

El documento cubre tres modalidades:

\begin{enumerate}
  \item \textbf{Desarrollo desde el código}: clona el repositorio y construye las imágenes localmente.
  \item \textbf{Vista local de entrega}: añade Nginx en el puerto 8080 y reutiliza la API y las bases de desarrollo.
  \item \textbf{Ejecución de una entrega completa}: descarga imágenes de GitHub Container Registry (GHCR) en un proyecto Compose aislado.
\end{enumerate}

La versión actual conserva la infraestructura del Sprint 1 y el núcleo administrativo del Sprint 2. Sprint 3 añadió conexión SQL Server, introspección y asistente supervisado; Sprint 4 incorporó materialización y conciliación; Sprint 5 completó calidad semántica, analítica y reportería. Sprint 6 permite varias fuentes SQL Server habilitadas, aísla catálogo y expedientes por conexión y valida el mismo ciclo con AdventureWorks2022 y WideWorldImporters.

\section{Requisitos previos}

\subsection{Hardware recomendado}

\begin{itemize}
  \item Procesador de 64 bits con virtualización habilitada.
  \item 8 GB de memoria disponibles para Docker; 6 GB es el mínimo práctico.
  \item 15 GB libres para imágenes, capas, respaldo y volúmenes; reservar al menos 8 GB adicionales si se descargará el modelo local de Ollama.
  \item Conexión a Internet durante la primera construcción y restauración.
\end{itemize}

\subsection{Software requerido}

\begin{itemize}
  \item Docker Engine 24 o superior y Docker Compose v2; Docker Desktop es válido.
  \item Git para clonar y actualizar el repositorio.
  \item Acceso al repositorio público; permiso de escritura sólo para colaboradores autorizados.
  \item Para consumir imágenes públicas no se necesita iniciar sesión; si un paquete GHCR conserva visibilidad privada, se requieren credenciales con \file{read:packages}.
\end{itemize}

No se requiere instalar Python, Node.js, PostgreSQL, SQL Server, controladores ODBC ni LaTeX en el host.

En equipos ARM, incluido Apple Silicon, SQL Server usa \file{linux/amd64} mediante emulación. El primer arranque puede ser más lento.

\section{Instalación de desarrollo en este computador}

El proyecto se encuentra en \file{/home/ceo/Proyectos/BI}. Para una primera ejecución:

\begin{lstlisting}[style=terminal,language=bash]
cd "/home/ceo/Proyectos/BI"
cp .env.example .env
# Editar .env y cambiar todos los secretos ChangeMe_*
make bootstrap
\end{lstlisting}

\file{make bootstrap} realiza las siguientes acciones:

\begin{enumerate}
  \item valida o crea el archivo de configuración local;
  \item construye las imágenes propias;
  \item crea una red y tres volúmenes exclusivos;
  \item inicia PostgreSQL y espera su estado saludable;
  \item inicia SQL Server, descarga y restaura AdventureWorks si el volumen está vacío;
  \item crea y prueba el usuario \file{bi\_reader};
  \item aplica las migraciones Alembic pendientes;
  \item ejecuta el servicio \file{seed}, que incorpora sin duplicar el catálogo protegido aprobado;
  \item inicia FastAPI y después React;
  \item espera hasta que los cuatro servicios respondan correctamente.
\end{enumerate}

El primer arranque puede tardar varios minutos. Para observar la restauración:

\begin{lstlisting}[style=terminal,language=bash]
docker compose logs -f sqlserver
\end{lstlisting}

\section{Operación funcional de los Sprints 2 a 5}

El Sprint 2 se opera sobre el mismo ambiente levantado con \file{make bootstrap} o \file{make up}. No se crea una instalación ni un conjunto de contenedores adicional para seguridad: React, FastAPI y PostgreSQL ya contienen el incremento. La migración se aplica mediante el servicio \file{migrate}; después, el servicio \file{seed} carga de forma idempotente el catálogo protegido antes de iniciar FastAPI.

\subsection{Migraciones y datos semilla por equipo}

Cada volumen PostgreSQL pertenece exclusivamente al equipo que lo creó y nunca se transmite por GitHub. Cuando una programadora actualiza \file{develop} y levanta Compose, Alembic aplica el cambio de estructura y \file{seed} incorpora o actualiza los permisos, menús, rol administrador y cuenta inicial aprobados. Este orden permite que una base vacía quede operativa y que una base ya existente conserve sus datos locales no protegidos.

Para repetir sólo el catálogo base, sin borrar ni exportar PostgreSQL, se ejecuta desde la raíz del repositorio:

\begin{lstlisting}[style=terminal,language=bash]
make seed
\end{lstlisting}

La operación no duplica registros. No distribuye cuentas temporales, auditoría, contraseñas, tokens, configuraciones LLM ni datos de negocio. Una semilla demostrativa futura deberá ser sintética, opcional y aprobada con la especificación del módulo que la consuma.

\subsection{Acceso inicial y sesión}

El primer arranque crea la cuenta administradora inicial desde las variables de administración definidas en \file{.env}. Estos valores son secretos locales: se cambian antes de una demostración compartida y nunca se incorporan a Git, capturas ni bitácora. Se abre la interfaz en el puerto configurado, se ingresa con esas credenciales y se cierra la sesión desde el encabezado al terminar.

FastAPI valida la contraseña con Argon2 y entrega un JWT de vida limitada. React conserva únicamente el token de sesión necesario para consultar la API; el token no contiene contraseñas, claves LLM ni permisos que sustituyan la comprobación del servidor. Cada endpoint administrativo comprueba de nuevo el usuario activo y su permiso efectivo.

Los grupos se ordenan por el flujo de trabajo y se pueden plegar o desplegar, incluso si contienen la pantalla activa. Cada categoría y subopción incorpora un icono SVG junto a su texto, foco visible y estado activo por fondo y borde; la iconografía nunca sustituye el nombre accesible. En escritorio, el panel lateral se contrae o restaura mediante el chevrón de su borde; en tableta y móvil se abre con menú hamburguesa. Esta reclasificación ocurre sobre las opciones que FastAPI ya autorizó: una URL o petición directa sin permiso continúa recibiendo acceso denegado.

\subsection{Usuarios, roles, permisos y menús}

La administración no solicita IDs ni códigos técnicos a la persona usuaria. En \textbf{Usuarios}, se registra correo, nombre, contraseña inicial y roles mediante una tabla de casillas con nombre y descripción. Durante una edición, dejar la contraseña vacía mantiene la contraseña existente; escribir una nueva la reemplaza de forma segura.

En \textbf{Roles}, los permisos se asignan o retiran mediante otra tabla de casillas legible. La actualización de asociaciones usa el contrato \file{PUT /roles/\{id\}/permissions}; el código técnico interno del rol no se digita desde la pantalla. Permisos y Menús son catálogos controlados: una pantalla administrativa no puede inventar un permiso, ruta o módulo que no exista en una especificación, migración y endpoint reales.

Las listas administrativas son paginadas desde el servidor. Usuarios, Roles y Menús permiten crear, editar, activar/desactivar y, cuando corresponde, eliminar definitivamente. Las acciones de registros base de recuperación muestran el estado \textbf{Protegido}; FastAPI impide desactivar, eliminar o debilitar la cuenta y rol administrativos iniciales.

\subsection{Eliminación y auditoría}

Eliminar no significa ocultar un registro. Para una eliminación física permitida, la interfaz pide confirmación y FastAPI comprueba primero las asociaciones hijas. Por ejemplo, un rol con usuarios o permisos asignados no se borra hasta resolver esas relaciones; la API responde con conflicto y una explicación. No existe borrado en cascada silencioso.

Una cuenta temporal no protegida sí puede eliminarse después de retirar sus roles. Sus eventos de auditoría no son una dependencia bloqueante: la migración \file{20260911\_05} configura la referencia de actor con \file{ON DELETE SET NULL}. Al borrar la cuenta, el identificador técnico queda vacío, pero cada evento conserva la etiqueta histórica segura del actor (nombre y correo en el momento de la acción). Así se mantiene la trazabilidad sin conservar una cuenta de prueba ni borrar eventos de auditoría.

Toda mutación administrativa genera un evento de auditoría con actor, fecha, acción, tipo de recurso, identificador y resumen seguro. Se registran inicio de sesión, altas, actualizaciones, cambios de estado, asociaciones, pruebas de conexión y eliminaciones. La vista Auditoría es sólo de consulta, paginada e inmutable; para actores ya eliminados muestra la etiqueta histórica y nunca presenta contraseñas, JWT, API keys ni cadenas de conexión completas.

\subsection{Parámetros generales}

La pantalla Parámetros no es una tabla libre de clave/valor. Sólo muestra cuatro enteros operativos aprobados: \path{UI_PAGE_SIZE}, \path{CONNECTION_TIMEOUT_SECONDS}, \path{LLM_TIMEOUT_SECONDS} y \path{METADATA_BLOCK_MAX_ITEMS}. El catálogo analítico se administra en \textbf{IA > Catálogo analítico} con los permisos independientes \path{copilot.catalog.read} y \path{copilot.catalog.write}. Allí se gestionan preguntas de negocio y periodicidades por dominio y por fuente. El objetivo pertenece a cada análisis y las dimensiones no son un parámetro. FastAPI valida y audita cada cambio.

El catálogo tiene dos planos visibles. El \textbf{catálogo de negocio} pertenece al analista: define qué preguntas quiere ofrecer y con qué periodicidades. La \textbf{cobertura técnica} pertenece a la plataforma: se recalcula desde la instantánea seleccionada y muestra las tablas o columnas reales que respaldan cada capacidad. El LLM interpreta ambos planos y redacta una propuesta, pero no crea evidencia ni determina por sí solo que una capacidad existe. Después de cada respuesta, FastAPI vuelve a validar referencias, tipos, PK, FK, rutas, granularidad, fórmulas y cobertura.

El perfil de ventas aporta cuatro preguntas estándar: evolución temporal, producto, cliente y territorio. En la fuente AdventureWorks el analista añadió manualmente \textbf{Costos y rentabilidad de las ventas} y \textbf{Ventas y costos por unidad} después de recibir una recomendación conversacional. Estas entradas personalizadas pertenecen a esa configuración y no se copian a otra conexión. Una nueva fuente recibe la línea base; el analista decide si añade preguntas y la plataforma comprueba si sus metadatos permiten resolverlas.

Los tiempos máximos de conexión y LLM controlan sus respectivas operaciones. \file{LLM\_TIMEOUT\_SECONDS} inicia en 600 segundos y admite hasta 900 para modelos locales ejecutados por CPU; los proveedores cloud normalmente terminan antes. El tamaño de bloque participa en la preparación del contexto y el perfil de dominio aplica además un alcance técnico acotado para no enviar las 71 tablas completas a un modelo pequeño.

\subsection{Conexiones de datos}

La pantalla \textbf{Conexiones de datos} permite registrar nombre, servidor, puerto, base, usuario, contraseña y opciones controladas de cifrado para SQL Server. No acepta una cadena de conexión libre. La contraseña se cifra en \file{app.secrets}; React recibe sólo los campos no secretos y nunca recupera el valor guardado. Al editar, dejarla vacía conserva la credencial existente y cualquier cambio invalida la prueba anterior.

\textbf{Probar conexión} abre SQL Server con intención de lectura, consulta el catálogo y comprueba que la cuenta no pertenezca a \file{db\_owner} o \file{db\_datawriter} ni posea permisos de inserción, actualización, eliminación, creación de tablas o control. Una prueba fallida no puede habilitarse. Varias conexiones probadas pueden permanecer habilitadas al mismo tiempo; el selector del espacio de trabajo establece el contexto de la sesión y no altera el de otro usuario. FastAPI audita creación, edición, prueba, habilitación, deshabilitación y eliminación sin guardar cadenas completas.

En el entorno Docker académico se registra el host \file{sqlserver}, puerto 1433 y un usuario lector aprovisionado durante el arranque. AdventureWorks2022 y WideWorldImporters pueden coexistir en la misma instancia, pero cada una se registra como conexión independiente. Las variables de \file{.env} siguen siendo necesarias para construir la instancia local, pero la operación del flujo BI usa la credencial registrada desde la plataforma.

Cada captura conserva conexión, base, versión contractual, totales, actor histórico y fecha. La migración \path{20260918_08} impide eliminar una conexión que tenga instantáneas asociadas.

\subsection{Asistente de datamart supervisado}

La pantalla \textbf{IA > Asistente de datamart} requiere tres condiciones comprobables: fuente seleccionada, habilitada y probada en sólo lectura; instantánea vigente de esa fuente; y proveedor LLM activo con prueba satisfactoria. La entrada no abre directamente ventas: consulta \file{GET /api/v1/copilot/catalog} con \file{connection\_id} y muestra los dominios que disponen de perfil, metadatos y validadores. Sólo \textbf{Datamart de ventas} está implementado; un dominio futuro puede añadirse al catálogo sin crear otra pantalla.

Al elegir el dominio, el backend devuelve preguntas orientadoras y periodicidades compatibles con la instantánea. React no contiene un modelo dimensional fijo de AdventureWorks. El catálogo se administra por dominio desde \textbf{IA > Catálogo analítico}. Las preguntas guían la interpretación, pero no fijan tablas, columnas ni dimensiones. El analista BI continúa por cinco pasos:

\begin{enumerate}
  \item escribir el objetivo comercial, seleccionar preguntas orientadoras y escoger una periodicidad soportada;
  \item revisar conceptos de negocio propuestos en español y revelar, cuando se necesite, su origen técnico;
  \item examinar granularidad, hecho, medidas, dimensiones, uniones, KPIs y plan ETL declarativo;
  \item personalizar, de forma opcional, resumen, granularidad, dimensiones, medidas, agregaciones y KPIs ya verificados, con una justificación;
  \item aprobar o rechazar con comentario y confirmación explícita de advertencias.
\end{enumerate}

Cada intento se almacena en \path{app.bi_proposals} y queda ligado a la huella de la instantánea, proveedor, modelo, versión de prompt, entrada, mapa semántico, alcance, validación y decisión histórica del actor. Excluir conceptos, cambiar la necesidad o personalizar decisiones crea otra versión; \file{source\_proposal\_id} conserva su origen y nunca sobrescribe el registro anterior. La personalización no llama al LLM y no admite tablas, columnas, relaciones ni fórmulas libres: \file{POST /api/v1/copilot/proposals/\{id\}/revisions} aplica únicamente selecciones válidas y repite la validación determinística.

Antes de invocar al proveedor, la pantalla separa los requisitos en cuatro estados. \textbf{Directo} identifica una referencia física comprobada; \textbf{Derivable automáticamente} identifica una fórmula tipada o una ruta compuesta exclusivamente por FK declaradas. Ninguno exige SQL ni selección manual de tablas. Al generar, FastAPI adjunta la evaluación a la propuesta, aplica las derivaciones inequívocas y construye la matriz necesidad--salida. Si una salida directa o derivable no queda materializada, la validación bloquea la aprobación. Sólo \textbf{Ambiguo} y \textbf{No disponible} requieren una decisión del analista.

La búsqueda de evidencia conserva un subgrafo coherente con toda la necesidad. No combina, por coincidencia nominal, medidas de compras con dimensiones de ventas. En la instantánea 2 se contrastaron 23 columnas críticas y siete FK contra SQL Server: fecha, cliente, persona o tienda, territorio, producto, categoría, cantidad, precio, descuento, importe y costo coincidieron en nombre, tipo y nulabilidad. La viabilidad de ventas parte de \file{Sales.SalesOrderDetail}; el costo llega a \file{Production.Product.StandardCost} mediante la relación compuesta declarada, sin depender de nombres de tabla fijos.

En cualquier fuente se excluyen del grafo de negocio las relaciones de auditoría. Esto incluye campos como \file{CreatedBy}, \file{ModifiedBy}, \file{UpdatedBy} y \file{LastEditedBy}. Una FK válida físicamente no demuestra que la entidad relacionada sea producto, cliente o territorio. Las tablas de compras, archivo, pruebas o preparación reciben penalización cuando existe evidencia comercial actual. Las dimensiones directas o derivables requeridas por la necesidad se incorporan desde esa evidencia aunque el proveedor las omita; si no pueden demostrarse, la aprobación se bloquea.

La sección \textbf{Versiones generadas} consulta el servidor por dominio y estado, muestra inicialmente \textbf{Lista para revisar} y pagina los resultados. Permite abrir cualquier artefacto persistido y escoger cuál revisar o aprobar sin volver a consumir el proveedor. Esto facilita preparar una ejecución local lenta antes de una demostración y conservar, al mismo tiempo, resultados cloud comparables. Los permisos \path{copilot.proposals.read}, \path{copilot.proposals.generate} y \path{copilot.proposals.review} separan consulta, generación y decisión.

Cuando se abre una versión histórica, el asistente restaura el objetivo, las preguntas y la periodicidad persistida; no reutiliza el valor predeterminado del dominio. Las cinco etapas quedan disponibles como consulta inmutable y la acción \textbf{Crear nueva propuesta} inicia un borrador vacío en el mismo dominio sin cerrar sesión ni modificar el expediente consultado. Esta salida elimina la dependencia operativa de reiniciar la sesión para continuar el trabajo.

En \textbf{Personalización}, cada medida separa su etiqueta de negocio del identificador técnico y muestra su origen calificado y su regla ejecutable. Por ejemplo, el conteo de transacciones expone \path{Sales.SalesOrderDetail.SalesOrderID} y \file{COUNT(DISTINCT SalesOrderID)}; una medida calculada muestra primero la expresión por fila y después la agregación. KPI, selectores y botones conservan el texto completo mediante una disposición adaptativa, evitando concatenaciones como \file{importe\_brutoImporte de ventas}.

\subsection{Validación acumulativa visible}

La versión seleccionada incorpora \textbf{Validación estructural de la propuesta - Sprint 3}. La acción \textbf{Verificar evidencia} llama a \file{POST /api/v1/copilot/proposals/\{id\}/verify}; FastAPI no vuelve a consumir el LLM ni ejecuta el ETL. Comprueba la huella de los metadatos, referencias técnicas, consistencia del contrato BI y reproducción determinística desde \file{ai\_decisions}. Para propuestas creadas con la versión vigente del motor, la propuesta persistida y la reejecutada deben tener la misma huella SHA-256. En propuestas históricas, una diferencia debida exclusivamente a la evolución del motor se presenta como advertencia de compatibilidad y no como error de datos.

Este control permite al analista BI verificar en Sprint 3 que la estructura utilizada procede del OLTP y que la propuesta aprobada no cambió. Sprint 4 agrega un expediente de ejecución independiente que compara filas al grano aprobado, pedidos distintos, unidades, importes y KPI entre AdventureWorks OLTP y el datamart. Sprint 5 agrega cobertura descriptiva, paneles sobre agregados conciliados, chat seguro y reportes fieles. AdventureWorksDW permanece como contraste secundario, no como fuente primaria de verdad. El juicio de expertos pertenece al cierre académico; pronóstico, MAPE y RMSE fueron retirados del alcance por decisión del tutor.

Cada comprobación muestra \textbf{Cumple} o \textbf{Revisar}; el evento \file{copilot.proposal.verify} conserva identificador y prefijos de huella sin metadatos completos, filas ni secretos. La reproducibilidad se refiere a reejecutar decisiones persistidas con reglas determinísticas, no a exigir que dos llamadas nuevas al LLM generen exactamente la misma respuesta.

El LLM no constituye la autoridad técnica. Primero interpreta conceptos y luego devuelve decisiones compactas de hecho, medidas, dimensiones y KPI mediante un esquema JSON construido desde el alcance. FastAPI completa mecánicamente PK, FK, atributos, reglas y operaciones ETL; conserva las decisiones originales bajo \file{ai\_decisions} y valida el contrato expandido. También bloquea instrucciones SQL o ejecutables en la entrada y en la respuesta. Una propuesta con errores permanece en \textbf{Validación fallida}; sólo una versión válida pasa a \textbf{Lista para revisar}.

Cada medida y KPI declara una función tipada: importe, cantidad, conteo de clientes o conteo de transacciones. FastAPI contrasta esa función con columna, agregación y operación, y excluye un KPI que apunte a una medida incompatible. Las frases libres del proveedor se conservan como observaciones de trazabilidad, separadas de ajustes automáticos y advertencias determinísticas. El analista puede excluir o reasignar un KPI a otra medida compatible ya verificada; si no existe, la interfaz explica que debe retirar el KPI o generar una propuesta con la medida faltante. Las dimensiones proceden de la propuesta del LLM y sólo sobreviven cuando sus fuentes pertenecen al alcance verificado; la prueba real identificó \file{dim\_fecha} desde \file{Sales.SalesOrderHeader.OrderDate}. Sin una fuente comprobable, no se inventa.

La aprobación no crea tablas ni ejecuta transformaciones. Produce un contrato humano y técnicamente aceptado que el módulo ETL puede seleccionar después. La propuesta aprobada compatible más reciente se preselecciona, pero el analista debe confirmarla y puede comparar otras aprobadas; cada ejecución conserva el identificador elegido. El perfil \path{ventas} encapsula reglas semánticas, periodicidades soportadas, términos de descubrimiento, destinos y validadores; las preguntas se administran en el catálogo. El registro de conectores desacopla la lectura canónica del motor. Añadir inventario o MySQL exige implementar y probar el perfil o adaptador correspondiente antes de exponerlo.

Una aprobación puede retirarse desde la web con motivo obligatorio y una versión no aprobada puede descartarse. No se eliminan físicamente los registros porque conservan evidencia y auditoría. La migración \file{20260920\_13} amplía la restricción de estados de \file{app.bi\_proposals} con \file{invalidated} y \file{discarded}, evitando divergencias entre la lógica de aplicación y PostgreSQL. La verificación invalida una propuesta aprobada sólo cuando detecta un error bloqueante vigente; una diferencia histórica del motor no basta. Si una aprobación fue retirada por una comprobación anterior y ahora supera las reglas, \file{POST /api/v1/copilot/proposals/\{id\}/restore-approval} permite restaurarla con motivo y confirmación de advertencias, dejando evento de auditoría. El constructor del Sprint 4 repite esta comprobación inmediatamente antes de aceptar el contrato; un estado histórico por sí solo nunca autoriza el ETL.

\subsection{Materialización controlada del Sprint 4}

La pantalla \textbf{Datos > Datamart de ventas} guía cinco pasos: elegir propuesta, revisar indicadores, confirmar ejecución, materializar y validar. Sólo aparecen contratos con aprobación vigente, instantánea disponible, fuente habilitada de sólo lectura, referencias válidas y aptitud dimensional. FastAPI repite esas comprobaciones inmediatamente antes de preparar la ejecución; una aprobación histórica por sí sola nunca autoriza el ETL.

El analista revisa una cantidad variable de KPI sugeridos por la IA. Cada indicador muestra nombre, propósito, medida, periodicidad, unidad y receta compilada. Las recetas permitidas son agregación, razón y participación; las medidas calculadas aceptan únicamente operaciones aritméticas tipadas y columnas verificadas. No existe un campo de SQL ni una fórmula libre. Si una tasa de descuento se usa como importe, el backend exige precio, tasa y cantidad inequívocos y construye \file{precio * tasa * cantidad}; si no puede demostrarlo, bloquea la ejecución.

Al confirmar, \file{POST /api/v1/etl/executions} conserva propuesta, instantánea, selección de KPI, plan, validación, versión del constructor y responsable. La materialización se ejecuta desde FastAPI con la cuenta de origen de sólo lectura y publica cada carga nueva en un esquema controlado propio, \file{mart\_ventas\_e\{id\}}. Dentro de ese esquema la sustitución de tablas es transaccional, pero otra ejecución no se elimina. Las dimensiones reciben claves sustitutas y conservan las claves de negocio; el hecho se carga al final. El esquema legado \file{mart\_ventas} sigue siendo consultable para la última carga anterior al versionado.

El paso \textbf{Validar resultados} compara origen y destino y muestra filas, diferencias, tablas, KPI y estado. Para la ejecución 6 leyó y cargó 121317 líneas, con diferencia cero; calculó seis KPI, 274914 unidades y 31465 pedidos distintos. Los importes se muestran con código ISO sólo después de comprobar una moneda única relacionada con el hecho. AdventureWorks confirmó \file{USD} mediante \path{Sales.CurrencyRate.FromCurrencyCode}; la acción \textbf{Comprobar divisa sin repetir el ETL} enriqueció el expediente existente sin volver a cargar filas. Una fuente mixta o ambigua conserva \textit{moneda de origen} y explica la evidencia faltante.

La prueba multifuente produjo la propuesta 96 y la ejecución 13 sobre WideWorldImporters. El ETL cargó 231412 líneas de origen y destino, diferencia cero, 73595 pedidos y 9310904 unidades. Calculó 177634276,40 de ventas, 88904313,90 de costo y 88729962,50 de margen bruto. Las dimensiones publicaron 227 productos, 663 clientes y 53 territorios con etiqueta descriptiva. Como la estructura no demostró una moneda ISO única, la interfaz mantuvo \textit{moneda de origen}; como tampoco demostró descuento, lo registró como limitación en vez de inventarlo.

La interpretación de categorías se ejecuta después de la conciliación numérica. Sólo considera valores descriptivos, no sensibles y de baja cardinalidad; conserva el dato original y propone una columna española separada. La transformación se anuncia como \textbf{Revisar en el paso 5}. Allí el analista puede corregir, excluir o publicar cada mapeo y debe confirmar su revisión. La ejecución 6 publicó \file{group\_es} para Europa, Norteamérica y Pacífico, sin traducir códigos de país.

La tabla \textbf{Expedientes recientes} permite reabrir cualquier ejecución sin repetir la carga. Si la misma propuesta y selección de KPI ya tiene un expediente preparado, en curso, conciliado o pendiente de revisión, el botón de materialización se reemplaza por \textbf{Abrir expediente}; FastAPI aplica el mismo bloqueo dentro de una transacción. Sólo una ejecución fallida permite un reintento controlado.

Una propuesta aprobada conserva \textbf{Necesidad}, \textbf{Conceptos}, \textbf{Propuesta}, \textbf{Personalización} y \textbf{Revisión} como pestañas de consulta. Del mismo modo, un expediente completado permite recorrer \textbf{Elegir propuesta}, \textbf{Revisar indicadores}, \textbf{Confirmar ejecución}, \textbf{Materializar y cargar} y \textbf{Validar resultados}. Los campos quedan deshabilitados y la cuarta etapa explica la materialización realizada sin ofrecer una nueva carga. Este recorrido permite sustentar y auditar el proceso completo desde la propia plataforma.

\subsection{Copiloto contextual para decisiones semánticas}

En el paso de conceptos, la confianza del LLM no equivale a validación. La plataforma agrega evidencia determinística de tabla, columnas, clave y relaciones. Los conceptos de confianza baja o sin respaldo suficiente nacen desmarcados. \textbf{Ver evidencia y cómo resolver} explica causa, riesgo y consecuencias; el analista no necesita abrir DBeaver ni escribir SQL.

Cada concepto puede abrir un diálogo contextual. La IA recibe el objetivo, las preguntas y la evidencia estructural permitida; nunca recibe filas, credenciales o SQL libre. Su respuesta separa recomendación, confianza, evidencia citada, riesgo y acción. \textbf{Aplicar recomendación} sólo cambia la casilla visible y deja la decisión final al analista. La migración \file{20260923\_15} conserva estas conversaciones con proveedor, modelo, responsable y fecha.

\subsection{Resolución descriptiva y ejecución corregida del Sprint 5}

La conciliación numérica no basta para publicar una dimensión. La ejecución 6 conservó correctamente la población de \file{Sales.Customer}, pero no recorrió las relaciones opcionales hacia personas y organizaciones; por ello \file{dim\_cliente} mostraba números de cuenta. No era correcto reemplazar la población por todas las filas de \file{Person.Person}, porque allí también existen empleados y otras entidades que no compraron.

El resolutor del Sprint 5 separa \textbf{población} de \textbf{identidad}. Parte de la entidad vinculada al hecho y recorre claves foráneas verificadas hacia atributos descriptivos. Clasifica ramas como persona, organización o entidad relacionada; combina nombres mediante operaciones tipadas, conserva un respaldo explícito y bloquea relaciones que multipliquen el grano. La decisión no depende de que una tabla se llame \textit{Customer} o \textit{Person}: usa función semántica, relaciones, tipos, cobertura y atributos.

Antes de aprobar una propuesta, la interfaz permite \textbf{Revisar identidad de dimensiones}. Presenta cobertura, número de entidades, registros sin nombre, origen, columna destino y una muestra limitada de clave, tipo y etiqueta. La muestra permanece dentro de la plataforma y no se envía al LLM. Una ruta inequívoca se aplica automáticamente; una cobertura insuficiente bloquea la publicación y conduce a una nueva versión supervisada, sin DBeaver ni SQL libre.

La propuesta 54 produjo la ejecución 7. El datamart conserva 121317 líneas, 274914 unidades y 31465 pedidos sin diferencia. \file{dim\_cliente} contiene 19820 filas: 19119 personas y 701 organizaciones; todas disponen de \file{nombre\_cliente} y \file{tipo\_cliente}. Las claves \file{CustomerID}, \file{PersonID}, \file{StoreID} y \file{AccountNumber} permanecen para linaje y conciliación.

\subsection{Analítica explicable y conversación contextual}

La opción \textbf{Análisis y decisiones > Analítica de ventas} abre únicamente una ejecución exitosa y conciliada. La vista ejecutiva prioriza KPI, evolución, productos, territorios y hallazgos; la vista analítica habilita selección de indicador, clientes principales, tablas de respaldo y calidad. Año y territorio se aplican en el servidor a KPIs, gráficos, hallazgos y exportaciones. La moneda se muestra como \file{USD} porque fue comprobada en la fuente, no inferida por un símbolo.

Los gráficos admiten exploración directa con ratón, toque o teclado. Seleccionar un punto, barra o categoría abre dentro de la tarjeta un detalle con etiqueta, valor exacto y participación sobre el conjunto visible; cerrar el detalle no altera filtros. En la distribución territorial aparece \textbf{Filtrar tablero por...} únicamente cuando la etiqueta coincide con una opción real del catálogo devuelto por FastAPI. Aplicarla actualiza conjuntamente indicadores, visuales y hallazgos; no se aceptan valores escritos libremente.

Las razones \file{costo\_por\_unidad} y \file{venta\_por\_unidad} no representan una fila o producto individual. Son promedios ponderados sobre el filtro vigente: \file{CostoTotal / UnidadesVendidas} y \file{VentasBrutas / UnidadesVendidas}. Por ello la interfaz utiliza \textbf{Costo promedio por unidad vendida} y \textbf{Venta promedio por unidad vendida}, muestra \file{USD por unidad} y conserva el valor exacto como ayuda aunque la tarjeta abrevie cifras extensas para evitar desbordamientos.

Los hallazgos determinísticos citan su evidencia y no explican causas. En particular, una diferencia entre el primer y el último mes visible se describe como comparación de extremos; no demuestra tendencia o causalidad y puede involucrar meses con cobertura parcial.

El bloque \textbf{Preguntar sobre estos resultados} está separado del panel de hallazgos. Ofrece preguntas guiadas para comprender, decidir e interpretar con cautela en modo ejecutivo, y para comparar, investigar o validar en modo analista. El servidor reconstruye la selección conciliada y envía al LLM sólo KPIs, puntos agregados, hallazgos, calidad, granularidad y filtros. No envía filas, credenciales ni SQL. La respuesta contiene explicación, evidencias, advertencia, preguntas de seguimiento, proveedor y modelo. Cambiar vista o filtros limpia el contexto anterior.

Para una pregunta como ``¿Cuáles son los 5 productos más vendidos en Europa?'', la primera llamada al LLM sólo completa un esquema JSON cerrado: indicador, dimensión, Top N, orden, año y territorio deben pertenecer a los catálogos enviados por FastAPI. El servidor valida esos valores y construye por código propio una consulta agregada parametrizada; nunca acepta SQL del modelo. La respuesta muestra la interpretación, el total del universo filtrado antes del Top N, la participación de cada elemento y la procedencia de medida, operación y agrupación.

\subsection{Recuperación después de vencer la sesión}

Una respuesta HTTP 401 activa el estado global de sesión vencida y conserva la ruta de trabajo. El navegador guarda únicamente el objetivo redactado, códigos de preguntas, periodicidad, paso y el identificador de una versión persistida. Después de iniciar sesión, React vuelve al asistente y obtiene la propuesta mediante \file{GET /copilot/proposals/\{id\}} con los permisos renovados. No se guarda el documento completo, la respuesta del LLM, una credencial ni una operación pendiente. El cierre voluntario de sesión elimina también el borrador.

Los mensajes distinguen sesión vencida (401), permiso insuficiente (403) y servicio temporalmente no disponible (503). Los globos de preguntas usan texto blanco sobre fondos \file{\#2166e8} y \file{\#1f63dc}; sus contrastes calculados son 5,08:1 y 5,42:1, superiores al mínimo AA de 4,5:1 para texto normal.

Si una excepción inesperada ocurre durante el renderizado, el límite global de la interfaz muestra \textbf{El expediente sigue seguro} y ofrece recargar. La recuperación no ejecuta nuevamente el ETL. Al abrir un expediente desde el historial también se restablece el desplazamiento al inicio del comprobante, evitando que una posición antigua se perciba como una página en blanco.

La ejecución 9, asociada con la propuesta 73, conserva el expediente completo de referencia. Una carga posterior, la ejecución 10 generada desde Anthropic, sustituyó físicamente el esquema legado antes de introducir el versionado y por ello es la única versión antigua que todavía puede consultarse. La analítica no confunde expedientes históricos con datos disponibles: muestra la ejecución 10 como cobertura parcial y omite la 9 del catálogo analítico, aunque ambas continúan disponibles para auditoría. Cuando existe un solo datamart físico se presenta como \textbf{Datamart activo} sin un selector redundante y se ofrece acceso a los expedientes; el combo \textbf{Datamart analizado} aparece sólo desde dos alternativas realmente consultables. Las cargas creadas con la versión vigente quedan en \file{mart\_ventas\_e\{id\}} y pueden compararse sin repetir ni destruir el ETL anterior.

Al seleccionar un punto, barra o territorio, el detalle mantiene nombre, valor, participación y acciones dentro de la tarjeta. La rejilla adapta sus columnas al ancho disponible y permite partir cadenas extensas; por tanto, un valor monetario largo o una etiqueta descriptiva no debe superponerse con la tarjeta contigua. Esta regla debe comprobarse en vista ejecutiva, analítica y resolución móvil.

La corrección es neutral al proveedor. Gemini, Groq, Anthropic, Qwen y Ollama pueden redactar nombres distintos, pero FastAPI compila medidas y dependencias a identificadores técnicos. Los KPI con la misma medida, operación y función se consolidan; \file{AVG(LineTotal)} se muestra como \textbf{Importe promedio por línea de venta}, mientras que \textbf{Venta promedio por unidad vendida} se calcula como suma de ventas dividida para suma de unidades. Una receta derivada que no resuelve sus entradas se presenta como \textbf{No calculable} y nunca recibe confirmación verde.

La ejecución 11 expuso un caso adicional cubierto por HBI-012. El ETL y su conciliación eran correctos, pero una fórmula podía depender directamente de medidas físicas autorizadas sin que existiera un KPI agregado redundante con el mismo nombre. El servicio de analítica construye ahora el conjunto de dependencias, agrega primero las columnas físicas necesarias y resuelve después las recetas derivadas en iteraciones hasta alcanzar un punto fijo. Si no hay avance, el indicador permanece como \textbf{No calculable} y cita la dependencia ausente; no se inventa un cero ni se inicia otro ETL.

La validación de la ejecución 11 recuperó margen bruto, margen porcentual, costo promedio por unidad y venta promedio por unidad tanto para el universo completo como para 2013--Europa. Este comportamiento no depende del orden del JSON ni del proveedor que redactó la propuesta, y conserva el filtro, la fórmula y los operandos utilizados en la respuesta.

La prueba integral del 29 de septiembre extendió esta neutralidad a la generación completa. Las propuestas 87--90 de Claude permitieron aislar, en orden, un incumplimiento de esquema, un texto mayor al límite declarado, una entidad vendedora confundida con cliente y una columna relacionada atribuida falsamente al hecho. La plataforma proyecta ahora cada respuesta al esquema común, elimina propiedades excedentes, respeta longitudes y cardinalidades, y realiza como máximo un reintento guiado. Después vuelve a validar el resultado localmente. La selección de identidad puntúa rutas FK, evidencia descriptiva y función compradora, penaliza empleado, vendedor y proveedor, y no depende de nombres específicos de AdventureWorks. Una medida directa sólo se conserva si su columna existe físicamente en el hecho; una medida opcional incompatible y sus KPI se excluyen con diagnóstico, mientras que la cobertura bloquea cualquier requisito obligatorio ausente.

La propuesta 91, generada con Claude Haiku a partir de la misma necesidad, superó los cuatro controles de evidencia con cero errores y cobertura de 19 de 19 requisitos. La dimensión \file{dim\_cliente} se construyó desde la entidad compradora y resolvió dos variantes descriptivas: persona mediante nombre, segundo nombre y apellido, y organización mediante nombre de tienda. La ejecución 12 materializó cinco tablas en \file{mart\_ventas\_e12}, cargó 121317 líneas, obtuvo diferencia cero y publicó 12 KPI calculables. \file{dim\_cliente} contiene 19820 clientes, 19820 nombres no vacíos y dos tipos: 19119 personas y 701 organizaciones.

\subsection{Exportación PDF y Excel}

Los botones \textbf{Exportar PDF} y \textbf{Exportar Excel} vuelven a construir la selección autorizada en FastAPI. PDF usa A4 horizontal, páginas deliberadas para resumen, tendencia, rankings, hallazgos y calidad; no captura el HTML ni corta tablas entre páginas. Excel conserva valores numéricos, formato de moneda o conteo, un resumen, una hoja por gráfico visible y, en modo analista, una hoja de trazabilidad. La vista ejecutiva no recibe contenido reservado al analista.

Cada descarga registra actor, formato, vista, ejecución, indicador y filtros. Los archivos no contienen macros, vínculos externos, credenciales, filas crudas, SQL ni fórmulas generadas por IA. La evidencia final de la ejecución 12 se revisó página por página y hoja por hoja. El PDF reserva espacio después de cada salto para impedir que un título quede fuera del margen superior; Excel conserva los porcentajes del dashboard en escala 0--100 y aplica el signo sin multiplicarlos nuevamente. El libro analítico contiene resumen, cuatro hojas con gráfico y datos visibles, y trazabilidad con origen, destino y diferencia.

\subsection{Configuración LLM cloud y local}

La pantalla Configuración LLM mantiene nombre, proveedor, URL validada, modelo, estado y resultado de prueba. Puede existir una sola configuración activa. Para Gemini, Groq, Anthropic o Qwen Cloud se guarda primero el registro y después se usa \textbf{Registrar credencial}; cuando ya existe, la acción cambia a \textbf{Reemplazar credencial}. La clave se envía una sola vez y nunca vuelve al navegador. La tabla sólo presenta \textbf{Credencial pendiente} o \textbf{Credencial configurada}.

El identificador del modelo se parametriza porque el catálogo del proveedor cambia. Gemini se probó con \file{gemini-3.6-flash}. Para baja latencia, Sprint 4 incorporó Groq Cloud con URL restringida \file{https://api.groq.com/openai/v1} y modelo \file{openai/gpt-oss-120b}. La pantalla incorpora \textbf{Nivel de razonamiento}: automático, mínimo, bajo, medio o alto. Para GPT--OSS en Groq, mínimo se traduce a \file{low}; bajo, medio y alto se conservan. La prueba reserva salida según el nivel y usa \file{include\_reasoning: false}; la generación aumenta el presupuesto según el contrato. Así se corrigió la clasificación del error 400 que aparecía cuando el razonamiento consumía la salida antes de completar el JSON. Cambiar URL, modelo o razonamiento invalida la prueba anterior.

Anthropic Claude usa exclusivamente \url{https://api.anthropic.com} y la ruta \file{/v1/messages}. El preset inicial es \file{claude-haiku-4-5-20251001} con nivel mínimo, recomendado cuando se dispone de poco saldo por su menor costo y latencia. \file{claude-sonnet-4-5-20250929} puede escribirse como modelo alternativo si la cuenta todavía lo autoriza y el análisis justifica mayor consumo. FastAPI envía \file{x-api-key} y \file{anthropic-version: 2023-06-01}, incorpora el esquema esperado a la instrucción, omite pensamiento extendido y vuelve a validar localmente el JSON antes de usarlo. La clave prestada se registra en la instalación local; no debe copiarse a \file{.env}, Git, capturas o documentos.

El validador local del contrato es común a todos los proveedores. Groq conserva JSON Schema estricto como primera opción y tres intentos acotados. Ante un rechazo de validación estructurada, el adaptador puede solicitar JSON simple con el mismo esquema incluido en la instrucción. Claude, Gemini y Ollama pasan por la misma proyección segura y disponen de un único reintento guiado cuando faltan propiedades obligatorias o los tipos son incompatibles. La respuesta se acepta únicamente si supera nuevamente el validador local; de lo contrario se descarta. Esta adaptación no completa datos de negocio, no cambia relaciones, fórmulas, necesidad, alcance ni proveedor.

FastAPI cifra la clave mediante cifrado autenticado y almacena únicamente el texto cifrado en \path{app.secrets}. La raíz criptográfica se genera automáticamente con permisos restrictivos en \path{/var/lib/bi-ia-secrets/master.key} y se conserva en el volumen \path{secret_key_data}, separado de PostgreSQL. Si se borra ese volumen, las credenciales existentes dejan de poder descifrarse y deberán reemplazarse desde la pantalla. No se copia el volumen entre equipos y no se versiona. \path{GEMINI_API_KEY} y \path{DASHSCOPE_API_KEY} ya no se utilizan.

Para probar una configuración cloud se registra la credencial, se usa \textbf{Probar conexión} y se revisa el aviso verde de éxito o rojo con causa segura. La prueba sale desde FastAPI, descifra sólo en memoria, tiene tiempo limitado y no envía datos del negocio. La auditoría conserva la acción y el proveedor, nunca la clave ni el contenido de la respuesta.

\subsection{Selección operativa de Groq o Claude}

La prueba de conexión es necesaria, pero no suficiente para seleccionar proveedor. El procedimiento de aceptación debe repetir una necesidad de referencia, generar una propuesta sin aprobarla y comprobar estado, errores, advertencias, cobertura, medidas y KPI. La comparativa del 27 de septiembre produjo los siguientes resultados:

\begin{itemize}
  \item Groq medio, propuesta 78: conexión correcta y salida estructurada incompleta;
  \item Groq alto, propuesta 79: conexión correcta y límite temporal después de los reintentos;
  \item Claude medio y alto, propuestas 80 y 81: contratos completos, pero dos errores bloqueantes de referencia/procedencia y tres advertencias cada uno;
  \item Groq bajo, propuesta 73: cero errores y advertencias, ejecución 9 totalmente conciliada;
  \item Claude bajo, propuesta 77: cero errores, siete advertencias y resultado apto sólo para revisión.
\end{itemize}

Para este proyecto se configura \textbf{Groq bajo} como primera opción y \textbf{Claude Haiku bajo o mínimo} como respaldo. No se recomienda medio/alto para generar el contrato integral: Groq consume más presupuesto de salida o cuota, mientras que el adaptador Claude omite pensamiento extendido y esos niveles no cambian el esfuerzo efectivo. Si Groq falla por saturación, el analista activa Claude, prueba conexión y genera una versión nueva; nunca se reutiliza silenciosamente una salida fallida ni se aprueba una propuesta con errores. La metodología completa se conserva en el documento comparativo \url{docs/experiments/2026-09-27-groq-vs-claude.md}.

\subsection{Alternativa LLM local con Ollama}

Ollama es un respaldo opcional para probar la integración LLM cuando no se dispone de una cuota cloud o se desea evitar usarla. No reemplaza Gemini ni Qwen Cloud, no se inicia con \file{make up}, no requiere API key y no publica un puerto en el computador anfitrión. Sólo FastAPI, dentro de la red del proyecto, puede acceder al servicio por \file{http://ollama:11434}.

\subsection{Preparar y descargar el modelo}

Todos los comandos se ejecutan desde la raíz del repositorio. Antes de la descarga se recomienda comprobar que el equipo tenga al menos 8 GB de disco libre adicionales. El perfil inicia el servicio, pero no descarga automáticamente un modelo:

Esta opción se adopta como predeterminada porque ofrece respuestas directas en español con menor consumo que \file{qwen3:4b}. La descarga se conserva en el volumen \file{ollama\_models}. Por tanto, cada programadora debe ejecutar este procedimiento una vez en su propio computador: Git no versiona el modelo, GitHub Container Registry no lo publica y CI/CD no lo descarga.

\subsection{Registrar y probar la configuración}

Cuando existan migraciones de datos, la reversión deberá seguir el procedimiento de la versión específica. Nunca sustituir una migración por la copia manual de un volumen.

\section{Flujo Git y CI/CD}

\subsection{Desarrollo por rama}

La rama predeterminada \file{develop} integra el trabajo diario y \file{main} conserva únicamente entregas estables. Las ramas de trabajo parten de \file{develop} con los prefijos \file{feature/}, \file{fix/}, \file{docs/} o \file{chore/}.

\begin{lstlisting}[style=terminal,language=bash]
git switch develop
git pull --ff-only origin develop
git switch -c feature/nombre-cambio
# editar y comprobar
make verify
git add .
git commit -m "feat: descripcion breve"
git push -u origin feature/nombre-cambio
gh pr create --base develop --fill
\end{lstlisting}

El pull request hacia \file{develop} exige CI aprobada, una revisión y conversaciones resueltas. Cuando la iteración sea estable, se abre un segundo pull request de \file{develop} hacia \file{main}; esa promoción vuelve a ejecutar CI y, al fusionarse, activa CD. El procedimiento completo está en \file{docs/git-workflow.md}.

Las ramas \file{develop} y \file{main} tienen protección activa: impiden force-push y eliminación, exigen pull request, una aprobación, conversaciones resueltas y ocho controles de CI con la rama actualizada. La excepción administrativa se reserva para recuperación y debe justificarse en la bitácora.

\subsection{Integración continua}

En cada push y pull request hacia \file{develop} o \file{main}, CI:

\begin{enumerate}
  \item valida que los PR de trabajo lleguen a \file{develop} y que sólo \file{develop} promueva a \file{main};
  \item valida el archivo Compose;
  \item construye la etapa de prueba del backend;
  \item construye la etapa de prueba del frontend;
  \item construye las imágenes de infraestructura;
  \item compila los documentos LaTeX y verifica que los PDF versionados estén actualizados.
\end{enumerate}

Los trabajos de CI son efímeros: construyen y prueban contenedores en GitHub y los eliminan al terminar. No mantienen un servidor de desarrollo ni modifican los ambientes locales de los colaboradores.

\subsection{Entrega continua}

Después de un cambio en \file{main} o una etiqueta \file{v*}, CD valida y publica:

\begin{itemize}
  \item \file{prototipo-bi-ia-backend};
  \item \file{prototipo-bi-ia-frontend};
  \item \file{prototipo-bi-ia-postgres};
  \item \file{prototipo-bi-ia-sqlserver};
  \item \file{prototipo-bi-ia-docs}.
\end{itemize}

Las ejecuciones de línea base CI 32749237009 y CD 32749237059 finalizaron exitosamente para el commit \file{ddf2551}.

CD tampoco reemplaza automáticamente un servidor: publica imágenes con etiquetas \file{main}, \file{sha-*} y \file{v*}. Cada computador o proveedor de despliegue selecciona una etiqueta mediante \file{.env.release}. Así pueden coexistir desarrollo y producción sin compartir red, puertos ni volúmenes.

\subsection{Cierre propuesto en Azure}

Se recomienda Azure for Students para la demostración académica. La suscripción aporta crédito temporal, no alojamiento gratuito permanente. La arquitectura objetivo usa una VM Ubuntu x64 con 2 vCPU y 8 GiB, Docker Compose, alertas de presupuesto y apagado o desasignación fuera de las pruebas. SQL Server requiere x64 y consume una parte relevante de la memoria; una instancia gratuita mínima no es suficiente para el conjunto completo.

El despliegue seguirá esta secuencia:

\begin{enumerate}
  \item CI aprueba el pull request y la promoción \file{develop -> main};
  \item CD publica las cinco imágenes y una etiqueta inmutable;
  \item el ambiente GitHub \file{production} exige la aprobación definida por el equipo;
  \item GitHub Actions se autentica en Azure mediante OIDC y permisos limitados;
  \item la VM descarga la etiqueta, ejecuta Compose y comprueba salud;
  \item se registran SHA, digest, URL, resultado y cualquier reversión.
\end{enumerate}

La suscripción, la VM y el workflow de despliegue permanecen pendientes hasta que las autoras activen Azure for Students y confirmen región, presupuesto y nombres. No se almacenará una contraseña permanente de Azure en GitHub.

Dependabot trabaja contra la rama predeterminada \file{develop}. Las actualizaciones npm menores y parches se agrupan; los saltos mayores se revisan de forma intencional y separada para evitar mezclar migraciones incompatibles.

\subsection{Qué significa DevOps en este prototipo}

DevOps no es un contenedor adicional ni una persona distinta. En este proyecto es la práctica de mantener código, infraestructura, pruebas, documentación y entrega dentro del mismo ciclo trazable. Docker evita diferencias entre computadoras; Git conserva el historial; pull requests y protecciones controlan la revisión; CI comprueba cada integración; CD crea imágenes reutilizables; GHCR permite descargarlas; la bitácora y los PDF conservan la evidencia.

El responsable integrador trabaja en una rama de función, corre las verificaciones y abre el PR. Las colaboradoras pueden reproducir el ambiente, revisar, documentar y aprobar. Sólo la promoción aprobada de \file{develop} a \file{main} representa una entrega estable. GitHub Actions inicia CD automáticamente después de esa fusión: no hay que presionar un botón de despliegue local y tampoco se modifica una instalación de otra persona.

\section{Desarrollo guiado por especificaciones (SDD)}

\textbf{SDD} significa \emph{Specification-Driven Development}: antes de programar una capacidad se escribe una especificación breve, verificable y versionada. La intención es evitar que una idea, una propuesta de IA o un cambio de datos se transforme en código sin que el equipo haya acordado su alcance, sus límites y la evidencia que demostrará que funciona.

El Sprint 1 no se rehace con SDD porque ya se cerró como una base técnica. Desde el Sprint 2 la especificación es obligatoria para toda capacidad funcional nueva. Los archivos se conservan en \file{docs/specs/}; la guía es \file{docs/sdd-workflow.md} y \file{docs/specs/TEMPLATE.md} contiene la plantilla.

\subsection{Procedimiento SDD para cada función}

\begin{enumerate}
  \item Copiar la plantilla y crear un archivo con el identificador del sprint. Por ejemplo: \path{SPR-02-rbac-y-parametros.md}.
  \item Escribir el problema, objetivo, alcance incluido, exclusiones, actores, datos, API/interfaz, seguridad, criterios de aceptación, pruebas, riesgos y dependencias.
  \item Revisar y aprobar la especificación antes de implementar. Si la decisión afecta permanentemente la arquitectura, crear además un ADR en \file{docs/decisions/}.
  \item Crear la rama desde \file{develop}, implementar dentro del alcance y enlazar la especificación en el PR.
  \item Añadir pruebas; actualizar README, arquitectura, réplica, manual y bitácora cuando resulte afectado; ejecutar \file{make verify}.
  \item Con CI verde y revisión aprobada, fusionar hacia \file{develop}. Registrar el PR, SHA, evidencia y desviaciones en la bitácora.
  \item Promover \file{develop} hacia \file{main} únicamente cuando el incremento integrado sea estable. CD publicará las imágenes sin sustituir los volúmenes ni los equipos de desarrollo.
\end{enumerate}

\notebox{La especificación no sustituye las pruebas. Define qué se debe probar. En especial, cualquier propuesta de IA, SQL o ETL debe declarar aprobación humana, validaciones determinísticas, datos permitidos y auditoría antes de ejecutarse.}
