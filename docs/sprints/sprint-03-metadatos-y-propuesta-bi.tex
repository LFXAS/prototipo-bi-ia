\section{Resumen ejecutivo}

El Sprint 3 convierte la administración del Sprint 2 en el primer flujo analítico del producto. La aplicación registra y prueba una fuente SQL Server de sólo lectura, captura sus metadatos sin extraer filas, conserva instantáneas inmutables y permite explorarlas. Sobre una instantánea vigente, un proveedor LLM interpreta conceptos técnicos y produce una propuesta de datamart de ventas que FastAPI valida antes de una decisión humana.

El factor diferenciador no es un chat libre ni la generación directa de SQL. La IA reduce el trabajo técnico inicial al traducir metadatos, sugerir granularidad, hecho, dimensiones, KPIs y plan ETL. El software conserva el control: ninguna referencia inventada supera la validación y ninguna propuesta se ejecuta sin aprobación del analista BI.

\notebox{El Sprint 3 termina en un contrato aprobado o rechazado. La materialización del datamart, el ETL ejecutable, los dashboards y el pronóstico pertenecen a los sprints posteriores.}

\section{Objetivo y usuarios}

\subsection{Objetivo}

Construir un asistente web que, a partir de metadatos persistidos de una fuente de ventas, permita expresar una necesidad comercial, obtener una propuesta dimensional asistida por IA, comprobarla mediante reglas determinísticas y someterla a aprobación o rechazo auditado.

\subsection{Contrato de IA}

El backend envía estructura técnica, nunca filas ni secretos. El contexto se ordena y se acota mediante el perfil de ventas para que un modelo local pequeño no reciba objetos ajenos a la necesidad. La IA devuelve primero conceptos y después decisiones compactas de hecho, medidas, dimensiones y KPI. FastAPI expande esas decisiones con claves, atributos, relaciones, reglas y un plan ETL determinístico, y conserva \file{ai\_decisions} para la trazabilidad. No se envían dimensiones preseleccionadas desde el paso inicial: cada dimensión debe surgir de la propuesta y conservar una fuente inequívoca dentro del alcance verificado. Los errores del proveedor, JSON inválido y tiempos agotados producen estados persistidos y comprensibles.

\subsection{Validación antes de aprobación}

\begin{itemize}
  \item bloquea tablas o columnas inexistentes o fuera del alcance;
  \item acepta sólo \file{fact\_ventas} y dimensiones destino aprobadas;
  \item verifica uniones contra claves foráneas declaradas;
  \item limita agregaciones y operaciones del plan ETL;
  \item exige que cada KPI use una medida propuesta;
  \item detecta instrucciones SQL o ejecutables;
  \item obliga a confirmar advertencias antes de aprobar.
\end{itemize}

\subsection{Necesidades sugeridas y revisión previa verificable}

La auditoría del 3 de octubre detectó que la ayuda de redacción recibía sólo una huella
y no el esquema, y que algunas comprobaciones confundían la presencia global de una
columna con una ruta utilizable. El asesor común \file{need\_advisor} corrige esa frontera:
permite sugerir objetivos sin texto inicial, reformular una necesidad y analizar su
viabilidad con la estructura real. El modo de análisis debe conservar el objetivo
exacto. Las sugerencias presentan evidencia y límites, requieren adopción humana y
no modifican las preguntas del catálogo por fuente.

El contexto permitido incluye esquemas, tablas, columnas, tipos, claves y FK declaradas,
sin filas, muestras, propiedades de conexión ni credenciales. El envío exige
consentimiento para el destino LLM mostrado; si cambia, se solicita de nuevo. Un límite
explícito de tamaño evita que una estructura excesiva se trunque silenciosamente.

La evaluación combina interpretación IA y reglas determinísticas de existencia,
tipo y ruta. No acredita costos desconectados, importes textuales, inversión de FK
con multiplicación del grano ni facturas ajenas al hecho de pedidos. Una periodicidad
exige una fecha verificable; una fecha comercial exacta conectada prevalece sobre una
marca de modificación. La ausencia de evidencia produce un límite, no una fuente
inventada. Las reglas no contienen condiciones por nombre de base.

La migración \file{20261003\_19} incorpora \path{app.business_need_reviews}: actor,
instantánea, proveedor/modelo, evaluación y huellas de entrada y resultado. Generar
exige una revisión persistida coincidente con texto, preguntas y período. Cambiar
contexto invalida la evaluación y la interfaz descarta respuestas tardías. Los
requisitos IA conservan su identidad y se enlazan a capacidades controladas: disponer
de ventas y costos no cubre un margen si el contrato no contiene su resultado derivado.

Esta puerta comprueba respaldo estructural, no calidad de filas ni historia de costos.
No aprueba propuestas, no ejecuta ETL y no altera versiones aprobadas. La aceptación
de negocio, la validación del modelo y la conciliación siguen siendo etapas separadas.

La ampliación real de QA-NEED usó Claude Haiku con autorización de envío. Los primeros
intentos de WideWorldImporters fallaron por ancla, rutas o tipos, y el análisis rechazó
un objetivo parafraseado. Un control local sobre las mismas FK pasó cinco requisitos
directos: la causa no era una captura de metadatos rota. Se añadió un reintento acotado
con feedback específico, sin debilitar los validadores ni cambiar de destino.

En AdventureWorks hubo sugerencias con referencias válidas, pero afirmaciones de estado
no demostradas y una revisión que confundió \file{UnitPrice} con costo. Esta última
falló el criterio QA y originó un contraste semántico común español/inglés; la versión
\file{need-review-2} evita reaprovechar las evaluaciones anteriores al endurecimiento.
Una evolución temporal que mezclaba importe y fecha en un solo requisito de medida
también se rechazó; la corrección pide separar funciones, no aceptar tipos incompatibles.

La repetición WWI obtuvo una sugerencia utilizable y otra bloqueada; la viabilidad
final mostró seis requisitos directos, dos automáticos y cuatro advertencias, sin
no disponibles. Sólo después de aceptar explícitamente los cuatro límites se habilitó
generar. No se ejecutó ese botón ni un ETL nuevo. El control negativo sobre clima
externo detectó la información ausente y distinguió sensores de refrigeración de
evidencia climática; no aprobó por sí solo la necesidad.

\subsection{Expediente acumulativo de validación técnica}

La plataforma añade \textbf{Validación estructural de la propuesta - Sprint 3} para la versión seleccionada. Sin llamar otra vez al LLM, FastAPI verifica la huella de los metadatos, repite los controles de referencias y contrato y reconstruye la propuesta a partir de las decisiones IA guardadas. La operación es de sólo lectura: una diferencia entre la huella persistida y la reconstrucción actual se conserva como diagnóstico de compatibilidad, pero no altera el estado aprobado. La seguridad para una ejecución nueva depende de la instantánea, las referencias y los errores estructurales vigentes. Así, la reproducibilidad recae sobre el artefacto aprobado y el motor determinístico, no sobre obtener dos respuestas idénticas de un modelo probabilístico.

La vista separa las evidencias ya disponibles de las pendientes. En Sprint 3 confirma correspondencia estructural con el OLTP, pero no compara importes ni cantidades. Sprint 4 incorpora conciliaciones de filas, documentos, unidades e importes entre OLTP y datamart. El contraste secundario con AdventureWorksDW requiere equivalencia semántica y la evaluación formal por expertos pertenece al cierre académico. Pronóstico, MAPE y RMSE se retiraron del alcance por decisión del tutor; no se presentan como validaciones pendientes.

\section{Experiencia UI/UX}

El acceso \textbf{Asistente de datamart} presenta primero un catálogo genérico; sólo ventas se habilita porque es el perfil implementado y validado. Después, el analista avanza por cinco pasos: necesidad, conceptos, propuesta, personalización opcional y decisión. El objetivo se escribe para cada análisis; las preguntas y periodicidades proceden de un catálogo administrable por dominio. El paso inicial no muestra dimensiones: la IA debe proponerlas desde los metadatos y el backend debe comprobarlas antes de la supervisión humana. Las acciones de IA, las comprobaciones de la aplicación y la aprobación humana tienen etiquetas diferentes para evitar atribuir certeza automática al modelo.

La sección \textbf{Versiones generadas} filtra inicialmente \textbf{Lista para revisar}, permite cambiar de estado, pagina los resultados e identifica proveedor, modelo, fecha, estado y versión de origen. No se implementa drag and drop libre ni un editor SQL. La personalización controlada permite ajustar resumen, granularidad, dimensiones, medidas, agregaciones y KPIs existentes con justificación; el backend crea una versión derivada y vuelve a validarla. Esto cubre desviaciones razonables del modelo sin convertir el prototipo en una herramienta de programación.

La revisión de continuidad HBI-013 completa esta experiencia sin alterar el alcance del incremento. Una versión histórica restaura también su periodicidad y ofrece \textbf{Crear nueva propuesta} para abandonar el modo consulta sin cerrar sesión. En personalización, la etiqueta de negocio, el identificador técnico, la fuente y la fórmula se presentan por separado; un conteo distinto identifica de forma explícita la clave contada. Estas reglas convierten el historial en una herramienta de revisión y sustentación, no en un estado que bloquee el trabajo posterior.

La prueba de aceptación detectó que una propuesta podía asociar un KPI de clientes con una medida monetaria, mezclar observaciones libres del proveedor con advertencias comprobadas o no reconocer una fecha existente. La corrección incorpora funciones semánticas tipadas para medidas y KPI, compatibilidad de columna y agregación, exclusión explicada de decisiones incoherentes y reasignación supervisada. La revisión posterior eliminó las dimensiones predefinidas del paso inicial: ahora el LLM las propone y el backend acepta sólo referencias verificadas. Los ajustes automáticos, advertencias, decisiones excluidas y observaciones originales se presentan por separado con acciones concretas.

Para depurar versiones ya aprobadas, el analista puede retirar la aprobación con motivo obligatorio; los demás intentos pueden descartarse. Ambos estados quedan fuera del flujo operativo sin borrar linaje ni auditoría. Verificar una aprobación vuelve a ejecutar las reglas actuales, pero nunca cambia su estado. Los errores bloqueantes impiden una nueva materialización y requieren una decisión humana explícita para retirar la aprobación. La migración \file{20261001\_18} restauró de forma auditable las aprobaciones retiradas por el comportamiento automático anterior cuando existía un ETL conciliado. Sprint 4 repite el control antes de materializar sin modificar el expediente histórico.

\section{Extensibilidad controlada}

La instantánea usa un contrato canónico independiente del lector. \file{CONNECTOR\_READERS} registra adaptadores y actualmente habilita \file{sqlserver}. Para MySQL se deberá implementar lectura de \path{information_schema}, mapeo canónico, campos de configuración, prueba de sólo lectura y pruebas automatizadas antes de mostrarlo en la interfaz.

El perfil \file{ventas} reúne reglas semánticas, periodicidades soportadas, términos, destinos y límites. El catálogo funcional aporta preguntas dinámicas que orientan al LLM sin predefinir el modelo. Un futuro datamart de inventario requiere otro perfil, prompts, reglas, consultas de referencia y criterios de aceptación; una vez registrado aparecerá en la misma entrada. Parametrizar preguntas no convierte una opción de texto en un motor o dominio funcional.

\section{Límites y riesgos}

La matriz histórica anterior pertenece al cierre original. La adenda QA-NEED del
3 de octubre añade casos sintéticos en español e inglés, referencias inventadas,
tipos incompatibles, FK incompletas, consentimiento y cobertura real de requisitos.
El contraste determinístico local eligió \file{SalesOrderHeader.OrderDate} en
AdventureWorks y \file{Invoices.InvoiceDate} en WideWorldImporters, sin reutilizar la
evidencia de otra fuente. Los ensayos con datos sintéticos no demuestran exhaustividad
de todas las formulaciones posibles ni compatibilidad con motores no implementados.

El corte final de regresión de esta adenda aprobó \file{make test} con 231 pruebas
backend y 34 frontend, más Ruff, formato, Mypy, ESLint y TypeScript/Vite. El aviso
de deprecación Starlette/AnyIO no fue un fallo. Los 201/33 casos del corte previo
permanecen como evidencia histórica, no como conteo vigente; la reformulación AW
bloqueada sigue registrada como limitación funcional pese al éxito automatizado.

\begin{itemize}
  \item Un modelo de 3B es una alternativa local de respaldo y puede tardar varios minutos; la calidad final debe compararse con un proveedor cloud disponible.
  \item La prueba de conexión cloud ahora realiza una generación mínima, pues listar modelos no garantiza derecho de uso.
  \item Una propuesta válida sigue siendo una propuesta; las consultas de referencia y la ejecución determinística del Sprint 4 deberán comprobar cifras.
  \item Sólo el perfil ventas y el conector SQL Server están habilitados. La arquitectura prepara extensiones, pero no declara compatibilidad no probada.
\end{itemize}

\section{Criterio de cierre}

El incremento quedó técnicamente cerrado cuando código, migraciones, pruebas, documentación y entorno integrado superaron \file{make verify}. La aceptación se registró al integrar el PR \#35 en \file{develop} y promover el resultado mediante el PR \#36 hacia \file{main}.

\section{Conclusión}

Sprint 3 demuestra el núcleo del título: la IA interviene en la construcción semiautomatizada del datamart, mientras la aplicación valida y el analista supervisa. El resultado evita tanto el extremo manual de escribir SQL como el extremo inseguro de ejecutar una respuesta libre del modelo. El contrato aprobado será la entrada controlada para materializar y verificar el datamart de ventas en el siguiente sprint.
